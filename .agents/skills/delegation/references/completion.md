# Review, Finalization and Delivery

## Skill acceptance

- For skill edits, read [instruction-authoring](../../instruction-authoring/SKILL.md)
  and [skill-authoring](../../skill-authoring/SKILL.md), including its discovered
  general authoring guidance. Reuse the actual Runner primary and independent
  Reviewer for corrections and complete zero-finding reviews within existing
  pipeline budgets; do not spawn redundant reviewers.
- Review the complete resulting skill tree and consumers: discovery,
  frontmatter, metadata, relative links/anchors, required reading routes,
  examples and permission preservation. Every skill Markdown file, including
  references, stays within 100 physical lines. Preserve the current document
  owners and any stricter maintained-content conventions they impose.
- Keep canonical skills under `.agents/skills` and preserve `.claude/skills`
  as its existing symlink. Tracked text stays self-contained English without
  unrelated-project context, private routes, credentials or machine-local paths.
- Use the discovered general skill validator where accessible. Otherwise leave
  read-only operator acceptance pending against exact unchanged final committed
  bytes. Candidate validation does not satisfy that acceptance or replace local
  validation, mandatory authoring checks or independent review.

## Phase-owned acceptance

- Follow the [finalization skill](../../finalization/SKILL.md) and established
  instruction/documentation inventory. Read the exact frozen entry and its
  mandatory repository references under existing read authority; classify
  command/gate owners as validation infrastructure without recursive retrieval.
- Preserve the owning workflow's evidence domains and selected-file composition.
  Keep Runner-owned persisted additions out of role result fields; a raw
  all-path Git digest is not the composed infrastructure proof. Independently
  review actual bindings and drift under the owning contract.
- During `FINALIZE`, format first with `npm run format`, then complete the
  established non-mutating checks, ending with `git diff --check HEAD`.
  Selected runner-trusted commands execute only through Runner's persisted
  exact vectors, never in agent turns; return their `NOT_RUN` placeholders.
  Their agent-sandbox limitations do not block content repairs or semantic review.
- Leave staging, staged/index-relative inspection, alternate-index workarounds,
  staged checks and commit-message drafting to the owning authorized `COMMIT`
  or `HANDOFF` boundary. Candidate work never executes or attests finalization.
- Require the selected mode's distinct read-only terminal confirmation over
  exact finalized content, infrastructure and complete validation evidence;
  independent and combined modes retain independent Reviewer confirmation.
  Content repairs invalidate dependent acceptance: reconverge, revalidate
  affected checks, reinventory/recount the complete skill tree and renew
  whole-result review.
  Use existing coverage; add no unrelated runtime slow checks for instruction
  work. Never claim skipped checks or synthetic fixtures as live-provider proof.

## Repaired builds and integration

- After each repaired build is fully reviewed, committed under existing
  authorization, installed and verified active/usable, immediately notify the
  requesting user through an already authorized Telegram route. Do not wait
  for batching or audit completion. Distinguish committed, installed,
  activation-deferred and globally active outcomes accurately; pending
  activation does not establish global usability.
- Keep routing and credentials in runtime/user state. This guidance grants no
  messaging, restart, global-update, foreign-run or remote-write authority.
  Installation remains operator-owned and necessary only when actual release
  content changes; preserve user configuration and durable runs.
- Integrate reviewed changes through a fresh Runner gate against current target
  contracts. Never replace newer contracts with stale source content.
